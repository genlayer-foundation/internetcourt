The future of Internet Court is the future of the agentic economy. Every consortium member is working toward it from its own niche, each solving one piece of the puzzle and catching a glimpse of what the finished picture will look like.

Internet Court is our joint effort to organize those building blocks into a cohesive whole: one ecosystem where agents can do business with each other.

We are still early. This is where we are, and where we are going.

> A bundle of skills is not yet a path. The work ahead is turning one into the other.

### Where we are today

Right now, Internet Court is a plain skill of skills. One master skill routes to more than 90 protocol skills published by the teams across the stack, plus a small set of connectors we wrote ourselves.

That already has value. An agent installs one thing and can reach payments, wallets, escrow, identity, compute, and dispute resolution without hunting for each skill separately.

But it is still a repository of mostly disconnected skills. Each one knows its own protocol. None of them knows about the others. The rest of this roadmap is about closing that distance.

### First, measure how the skill routes

The first job, already in progress, is understanding how the master skill actually behaves. We give an agent a request, then check which skills it loads into context. Did it reach for the right ones? Did it miss a layer? Did it pull in ten skills when it needed two?

You cannot improve routing you have not measured, so this comes before anything else.

### Use cases that span the stack

Single-skill tasks are the easy part. The real test is a use case that crosses several layers: negotiate a job, lock funds in escrow, do the work, verify it, and settle a dispute if one comes up.

We are writing those use cases and running each one through our testing framework, with real agents and real models, asserting on what the agent actually did.

We want yours too. If you have a use case that crosses more than one protocol, open an issue on the [skill repository](https://github.com/internet-court/internet-court-skill) and we will add it.

### Integration skills, where agents fall short

When an agent fails a use case, the failure is almost never inside one protocol. It is in the handoff between two.

So we add integration skills exactly where agents fall short, and we keep them as generic as possible. The ideal integration connects one layer to the next without depending on any single vendor's skill. Where a specific protocol does need guidance, we add metadata in the master skill that tells an agent how that protocol's skill should work with the others, without touching the original.

One use case at a time, until agents can perform the full path on their own.

### Skills that improve themselves

Writing integrations by hand does not scale to every pair of protocols and every variant of every use case.

So we are automating the loop. We already do a version of this in house: give an agent a scripted use case, run it many times inside **GenSwarms**, see what works and what does not, and revise the skill with a genetic approach, keeping the variants that perform and discarding the rest. The goal is not the most detailed skill. It is the smallest and most generic one that still gets the job done.

One lesson so far: a skill tuned on one model does not automatically work on another. So candidates are tested across models, not just the one they were tuned on.

> The best integration skill is the shortest one that works.

### Teaching the models directly

Agents learn from what is written down. Much of what Internet Court teaches today through a skill could, in time, simply be something the models already know.

So we are investing in generative engine optimization: publishing clear, accurate material on how agentic commerce fits together, here on this blog, so it becomes a source the models learn from. If you want the latest, you install the skill. But if an agent a year or two from now handles the common cases without installing anything, that counts as success.

We do not know whether skills will still exist in five years. Right now they matter, because without the recipes agents get it wrong.

### Simulating the agentic economy

The most ambitious piece is a simulation: a working agent economy, with many agents discovering, negotiating, contracting, paying, executing, and disputing with one another.

Running thousands of agents used to mean thousands of machines. Three pieces change that for us:

- **SubZeroClaw**, a minimal agent runtime written in C that takes about 2 MB of RAM.
- **GenSwarms**, which runs and coordinates large groups of agents without needing a machine for each one. It already powers the Clerk agent.
- **Unhardcoded**, a model router that picks a model by policy, such as the cheapest one that can do the job, so no model has to be hardcoded.

The point of the simulation is to learn what agents actually need: which arrangements are enough when agreed up front, where renegotiation is required, and whether the skill really carries an agent through a whole deal.

We will build it one layer at a time. We start with the bottom half of the stack: contracts, payment and escrow, execution, and verification and disputes. Then we add negotiation. Then discovery, identity, and reputation, until all six layers are running together. Where a layer is not ready yet, we mock it, so we can see how the rest behaves.

The pieces of the agentic economy already exist.

Our job is to make them work as one.

This is just the beginning.
